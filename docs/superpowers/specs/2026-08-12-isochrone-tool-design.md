# 等时圈与多点可达性交集工具 — 设计文档

日期：2026-08-12
状态：设计已确认，待实现

## 1. 目标

给定一个或多个起点，计算各起点在不同时间阈值下的可达范围（等时圈），并对多个起点的可达范围做集合运算（交集 / 并集 / 差集），用于回答「我们在哪碰头」「服务覆盖到哪」「只有 A 能到的区域是哪些」这类问题。

第一版聚焦**中国大陆的公共交通（公交 + 地铁）**场景。

## 2. 范围决策与依据

### 2.1 为什么第一版只做公交

调研确认：高德的到达圈接口 `AMap.ArrivalRange` **只支持公交出行方式**，`policy` 参数仅有 `SUBWAY`（只坐地铁）、`BUS`（只坐公交）、缺省（公交+地铁）三个取值，不支持驾车、步行、骑行。

因此国内外的能力分布是反向的：

| 出行方式 | 国内（高德） | 海外（ORS / Mapbox） |
|---|---|---|
| 公交 / 地铁 | 原生支持，一个接口 | 均不支持，需 TravelTime 或自建 OTP |
| 驾车 / 步行 / 骑行 | 无原生接口 | 原生支持 |

在「主战场为国内」的前提下，公交是唯一能靠单个现成接口做到高精度的方式，故定为第一版范围。

### 2.2 后续阶段（不在本次实现范围）

- **阶段二 · 国内驾车/步行等时圈**：高德无原生接口。可行路径是用距离测量 API（`/v3/distance`，单次最多 100 个起点对 1 个终点，返回真实耗时）反向铺网格点批量求耗时，再用 marching squares 插值等时线。一个城市 30 分钟驾车范围约需 20~30 次请求。这是自行实现一套采样+插值算法，工作量显著大于调用单一接口。
- **阶段三 · 海外覆盖**：接入 OpenRouteService provider（支持 driving-car / foot-walking / cycling-regular，单次请求可传多起点多档位）。届时需在 provider 层出口做 GCJ-02 ↔ WGS-84 转换。

## 3. 架构

### 3.1 技术栈

- **地图与底图**：高德 JS API 2.0（`AMap.Map`、`AMap.Polygon`）
- **等时圈数据源**：`AMap.ArrivalRange` 插件
- **几何运算**：Turf.js **7.x**（`union` / `intersect` / `difference` / `simplify`）
- **框架**：React + Vite
- **部署**：静态托管，`npm run build` 产出 dist 目录
- **后端**：无。纯前端应用。

### 3.2 坐标系

**第一版全栈统一在 GCJ-02 内，不做任何坐标转换。** 地图、等时圈数据、几何运算全部使用高德坐标。

依据：布尔运算只要求所有输入处于同一坐标系，不要求特定坐标系。只要不引入 OSM 系数据源，坐标偏移问题不存在。面积计算会因 GCJ-02 偏移产生微小误差，在等时圈这一精度量级下可忽略。

坐标转换仅在阶段三接入 ORS 时才需要，届时它是 provider 层内部一个孤立、可单独测试的模块。

### 3.3 鉴权

高德 Key 在前端暴露，通过高德控制台的**域名白名单**约束。这是高德 JS API 的标准用法。

## 4. 数据模型

```ts
type Mode = 'transit' | 'driving' | 'walking' | 'cycling'  // 第一版仅 'transit' 有实现

type Origin = {
  id: string
  label: string                     // "家" / "公司" / "学校"
  lngLat: [number, number]          // GCJ-02
  mode: Mode                        // 第一版恒为 'transit'
  policy: 'ALL' | 'SUBWAY' | 'BUS'  // 映射到高德 policy：ALL 对应缺省
  thresholds: number[]              // 分钟，自定义模式下每点独立
  color: string
  visible: boolean
}
```

**时间阈值上限**：`ArrivalRange` 的 `time` 参数实际可用上限约 60 分钟，超出通常无意义或返回异常。档位设计限定在 15 / 30 / 45 / 60 区间内，UI 层强制该上限。

## 5. Provider 抽象层

这是本设计最重要的接缝：**provider 是整个代码库中唯一知道高德存在的地方。**

```ts
interface IsochroneProvider {
  id: string
  supportedModes: Mode[]
  fetch(req: {
    lngLat: [number, number]
    mode: Mode
    minutes: number
    options?: { policy?: 'ALL' | 'SUBWAY' | 'BUS' }
  }): Promise<GeoJSON.MultiPolygon>
}
```

### 5.1 契约

Provider **一律返回标准 GeoJSON MultiPolygon**，而非高德的 `bounds` 格式。几何运算层与渲染层不感知数据来源。

### 5.2 归一化（必须在 provider 内部完成）

`ArrivalRange` 回调返回的 `result.bounds` 是**多边形数组**——公交可达域沿各条线路撒开，天然是几十至上百块不连通区域，且各线路缓冲区相互重叠，可能存在自相交。

直接将其送入 Turf 做交集会得到错误结果或导致性能崩塌。因此 provider 出口前必须执行一次 `union` 归一化，保证输出是干净、无自交的规范 MultiPolygon。**下游拿到的永远是规范几何，这是契约而非实现细节。**

`AMap.ArrivalRange` 调用签名：`arrivalRange.search(lnglat, time, callback, { policy })`，回调形如 `(status, result)`。

### 5.3 缓存层

包在 provider 外面，key 为参数指纹：

```
`${providerId}|${lng.toFixed(5)},${lat.toFixed(5)}|${mode}|${policy}|${minutes}`
```

该 key 形状带来三个直接结果：

- 切换交集 / 并集 / 差集模式 **零请求**（纯几何重算）
- 点拖走再拖回原位 **零请求**
- 给某点新增一个档位，**只请求新增的那一档**

### 5.4 并发闸门

`ArrivalRange` 单次请求只能处理**一个起点、一个时间档**，故请求数为 `点数 × 档位数`。3 点 × 4 档 = 12 个并发请求，足以触发高德的 QPS 限制。

因此所有 provider 请求必须经过一个并发闸门：**同时在飞的请求不超过 4 个**，并配合指数退避重试。这是正确性要求——不做会随机丢失部分等时圈，而非性能优化。

## 6. 几何运算层

纯函数模块，输入输出均为 GeoJSON，不涉及网络与 UI。

### 6.1 两种档位模式

为消除「A 设了 [15,30,45] 而 B 只设了 [15,30]，45 档配对谁」这类残缺组合，模式本身即消除歧义：

- **同档配对模式**：档位**全局共享**（一组 thresholds），各点仍独立保有自己的 `mode` / `policy`。输出为每档一个结果几何，天然嵌套成多层。对应「我们多快能碰头」。
- **自定义模式**：解锁每点独立选择一个 `(mode, policy, minutes)` 三元组，输出单个结果几何。

切换模式时，全局档位与各点档位各自保留，互不摧毁。

### 6.2 三种运算

```
交集   origins.map(geom).reduce(intersect)
并集   union(...geoms)
差集   difference(baseGeom, union(...otherGeoms))
```

差集不对称，必须额外指定基准点，语义为 `A \ (B ∪ C ∪ …)`。UI 上体现为选中某点作为「主体」。

### 6.3 运算前 simplify（正确性前提）

公交等时圈 union 后顶点数极易上万，直接连续 `intersect` 会阻塞主线程。运算前统一用 `turf.simplify` 以约 10 米容差（≈0.0001°）预处理。等时圈本身精度远粗于 10 米，此举不损失有效信息，可将运算量降低一到两个数量级。

### 6.4 Turf 版本注意

使用 Turf **7.x**。其 `intersect` 签名已改为接收 FeatureCollection，与网络上多数 Turf 6 示例不兼容，实现时以 Turf 7 官方文档为准。

## 7. 界面

### 7.1 布局：单侧栏

左栏承载全部控件，地图占据剩余全部宽度。

- **左栏上半 · 起点列表**：每个起点一张卡片，含颜色标识、名称、出行策略（公交+地铁 / 只坐地铁 / 只坐公交）、档位选择、可见性开关
- **左栏中部 · 运算控制**：交集 / 并集 / 差集切换，档位模式切换（同档配对 / 自定义），差集模式下的基准点选择
- **左栏下半 · 结果摘要区**：固定位置，展示各档结果面积与空结果文案
- **地图**：各点原始等时圈以各自颜色半透明铺底（可逐点开关），结果几何以高对比描边 + 更实填充压在最上层

结果摘要区独立且固定，是因为空交集这类「无图形可看」的结果必须有稳定的文字落脚点。

### 7.2 加点方式

- 地图点击落点
- 搜索框按地名加点（`AMap.PlaceSearch`）——公交场景下「西二旗地铁站」这类输入远比坐标自然
- 点可拖拽，**在 `dragend` 触发重算，而非 `dragging`**

### 7.3 导出

结果几何一键导出 GeoJSON。内部本就是 GeoJSON，实现成本近乎为零，但使该工具可接入 QGIS 或后续分析流程。纳入第一版。

## 8. 失败处理

关键在于区分「出错了」与「结果就是这样」——空结果在数据形态上与请求失败相似，但对用户的含义完全相反。

| 情况 | 处理 |
|---|---|
| 某点某档请求失败 | 仅标记该格失败并支持单独重试，**不整体回滚**；其余档位照常显示。该档的集合运算结果标记为「不可用」并提示缺失来源，**不得用残缺的点集合代入计算**——否则会得出一个看似正常、实则错误的交集 |
| 起点周边无公交覆盖（郊区、水域） | 高德返回空 bounds。此为**有效结果**，显示「该点周边无公交可达数据」，不作为错误 |
| 交集 / 差集结果为空 | **有效结论**，结果区输出对应文案（如「两点在 30 分钟内无共同可达区」），地图不绘制几何 |
| Key 无效 / 域名未加白名单 | 唯一需要全局错误提示的情况，文案直指配置问题（此类失败必然源于部署配置） |

三种运算的空结果各有不同含义，需分别配置文案。

## 9. 测试策略

测试重点在几何运算层与 provider 转换层——逻辑密度最高且错误最不显眼。

- **几何运算层**：纯函数单元测试，无需网络。覆盖边界情形——完全不相交（交集为空）、完全包含（差集为空）、带洞的 MultiPolygon、单点输入（交集应等于自身）
- **Provider 转换层**：录制一份真实 `ArrivalRange` 响应作为 fixture，测试「高德 bounds → 规范 MultiPolygon」转换。重点测 union 归一化：输入一组相互重叠的多边形，断言输出无自相交
- **并发闸门与缓存**：以假 provider 测试，断言并发数不超上限、相同 key 不重复发起请求
- **端到端**：不做自动化。使用真实 Key 手工验证若干已知城市即可——为外部地图 API 搭建 E2E 的收益低于成本

## 10. 第一版明确不做

- 驾车 / 步行 / 骑行等时圈（国内无原生接口，见 2.2）
- 海外区域与坐标转换（见 2.2）
- 结果分享链接、状态持久化到服务端
- 共同可达区内的 POI 检索
